# TLS termination

Every persona container generated by `pnpm gen:persona-edges` — the six
nginx configs under `deploy/persona-edges/` — serves plain HTTP. That's
correct for local development and for the docker-compose demo stacks
(`scripts/stack-up.sh`), and it's also the single biggest blocker to a real
customer deployment: every login, KYC field, and credential claim currently
crosses the wire unencrypted.

This directory adds TLS as a **separate layer in front of** those containers,
rather than a change to them, for two reasons:

1. The generated nginx configs are tested byte-for-byte against
   `packages/core/src/shared/personas.ts` (`persona-edge-config.test.ts`).
   Baking certificate paths into that generator would make its committed
   output depend on deployment-specific values that don't exist in CI or in
   a fresh checkout, and risk drifting the two apart.
2. Container-to-container traffic inside the docker network never leaves the
   host — only the internet-facing hop needs encrypting, so termination one
   layer up is both simpler and the more common production shape (a load
   balancer or CDN in front of plain-HTTP origins).

## What's here

- **`Caddyfile`** — one reverse-proxy block per persona container (12 total:
  6 web frontends + 6 API edges), keyed by subdomain. Caddy requests and
  renews Let's Encrypt certificates for each hostname automatically on
  first start — no cert files, private keys, or renewal cron to manage.
- **`docker-compose.tls.yml`** — one Caddy service, joined to the same
  external `xi-net` network the identity and tokenization stacks already
  use, so it reaches every persona container by its compose service name
  with no other wiring.

## Using it

1. Bring up the stack(s) you want to front, as usual:
   ```bash
   bash scripts/stack-up.sh identity tokenization
   ```
2. Point DNS at this host for every hostname in `Caddyfile` (or edit the
   file first to use your own subdomain scheme — nothing requires the
   `issuer.identity.example.com` pattern shown there, only that each
   block's `reverse_proxy` target matches a real compose service name).
3. Start Caddy, with ports 80 and 443 reachable from the internet:
   ```bash
   DOMAIN=example.com docker compose -f deploy/tls/docker-compose.tls.yml up -d
   ```

## What this doesn't cover

- **A real domain.** `{$DOMAIN}` in `Caddyfile` is a placeholder — there is
  no default, and Caddy will fail its ACME challenge against DNS it doesn't
  control. That decision belongs to whoever is standing up the deployment,
  not to this scaffold.
- **A CDN or corporate load balancer instead of Caddy.** If TLS is already
  terminating somewhere upstream of this host (a cloud load balancer, an
  existing reverse proxy), point it at the persona containers' existing
  HTTP ports directly and skip this directory entirely — Caddy is one
  reasonable default for a self-hosted deployment, not a requirement.
- **mTLS, HSTS tuning, or custom cipher policy.** `Caddyfile` uses Caddy's
  defaults throughout, which are reasonable for a pilot; a security review
  ahead of a larger rollout should revisit them deliberately rather than
  inherit them by omission.
